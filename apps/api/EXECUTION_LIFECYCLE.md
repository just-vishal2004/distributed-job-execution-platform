# Execution lifecycle

PostgreSQL is authoritative for job, worker, attempt, and lease state.

## States and transitions

| Entity | States | Transitions |
| --- | --- | --- |
| Job | `pending`, `queued`, `running`, `completed`, `failed`, `cancelled` | `pending` to `queued` on assignment; `queued` to `running` on start/progress; active to `pending` after a retryable failure or expired lease; active to `completed` on completion; active to `failed` after retry exhaustion; `pending`, `queued`, or `running` to `cancelled`. |
| Execution attempt | `assigned`, `running`, `completed`, `failed`, `timed_out`, `cancelled` | `assigned` to `running` on start/progress; active to `completed` on success; active to `failed` on worker-reported failure; active to `timed_out` on lease expiry or graceful deregistration; active to `cancelled` when its job is cancelled. Terminal attempts are immutable. |
| Worker | `idle`, `busy`, `revoking`, `dead` | `idle` to `busy` on assignment; `busy` to `idle` after normal completion or failure; `busy` to `revoking` when cancellation or lease recovery closes work; `revoking` to `idle` only after exact-attempt stop acknowledgement; stale or deregistered workers become `dead`. Dead workers must register again. |

`completed`, `failed`, and `cancelled` jobs are terminal. `completed`, `failed`, `timed_out`, and `cancelled` attempts are terminal. The partial unique indexes allow at most one active attempt per job and per worker.

## Retry semantics

`max_retries` means retries after the initial attempt. `retry_count` counts retries already consumed, so the initial attempt number is `retry_count + 1`. An attempt failure or expiry schedules another attempt while `retry_count < max_retries`, incrementing the count once. Otherwise the job becomes terminal `failed`. For example, `max_retries = 3` permits attempt numbers 1 through 4.

Each assignment creates the execution attempt in the same transaction as the job and worker state updates. Registration issues a random worker credential once and stores only its SHA-256 hash. Worker poll, heartbeat, and deregistration calls require that credential. A random UUID lease token identifies a specific attempt. Poll returns it only after worker authentication; start, progress, completion, and failure must present it. The lease token is stored in PostgreSQL as a bearer secret and is never written to application logs. Database access must remain restricted, and worker traffic must use TLS in production. A token for a prior attempt cannot change a newer attempt.

Workers renew leases only while `lease_expires_at > clock_timestamp()` in PostgreSQL. Start, progress, completion, and failure callbacks lock the job and attempt, then check expiry using PostgreSQL time after acquiring those locks. An expired lease cannot be renewed while waiting for recovery. Recovery locks the job then attempt, rechecks expiry, and processes each attempt once. Expiry times out the attempt, applies the retry rule, and leaves the worker revoking or dead depending on heartbeat age. A retry can overlap the old process or an external operation that continued after lease loss.

Cancellation locks the job, then its active attempts, then workers. It sets active attempts to `cancelled`, sets the job to `cancelled`, and moves assigned workers to `revoking`. It never makes those workers schedulable as part of cancellation. Cancellation applies to pending, queued, and running jobs. Repeating cancellation returns the cancelled job and resolves any legacy active attempt without reopening the job. Completion and cancellation serialize on the job row: whichever transaction obtains that lock and commits first determines the terminal outcome. Recovery and graceful deregistration preserve `cancelled` and never retry a cancelled job.

An active worker heartbeat includes the exact execution ID, job ID, and lease token. The API renews only that attempt; a missing, terminal, cancelled, expired, or mismatched attempt returns lease loss. Heartbeat responses label healthy idle and active states separately. An idle heartbeat is accepted only when the worker is idle and has no active attempt. The worker uses bounded requests, retries 429 responses with bounded exponential backoff, and aborts its local task on lease loss. An acknowledgement is accepted only for an attempt already marked `cancelled` or `timed_out` and a worker in `revoking`; the job, attempt, and worker are locked and checked in one transaction. Duplicate acknowledgements are idempotent and cannot idle a worker with another active attempt or unacknowledged revocation.

A settled task promise means only that the promise returned by the task runner has completed. It does not prove that detached asynchronous work or an external operation stopped. A worker process being retired or marked `dead` likewise does not prove an external operation stopped. Lease expiry and retry can therefore produce overlapping attempts. This system provides at-least-once execution, not exactly-once execution. Task handlers must make external side effects idempotent or use external fencing where available.

If execution is uncertain, operators should keep the affected work under review, inspect execution logs and the external system, and confirm the old worker process is stopped or isolated before manually reconciling. Preserve execution history. Do not mark a worker idle to resolve uncertainty. A dead database row prevents that worker identity from receiving assignments, but is not evidence that an external operation ended.

State-changing transaction paths use this row order where applicable: job, execution attempt, worker. Assignment locks the pending job before the idle worker and inserts its attempt in the same transaction. Callback, cancellation, heartbeat, recovery, revocation acknowledgement, and deregistration paths lock the job before the execution and update the worker last. Recovery processes a bounded ordered page of candidates per pass and advances a process-local keyset cursor even when a candidate fails. Failures remain eligible for a later pass and are logged. Multiple API processes have independent cursors and rely on PostgreSQL row locks.

**Verification evidence:** Historical Phase 2B engineering reports describe six lifecycle concurrency scenarios run against disposable PostgreSQL. Those report artifacts and runnable lifecycle concurrency tests are not present in this checkout, so the results cannot be reproduced from a fresh clone. The checked-in PostgreSQL integration test covers email verification, not lifecycle concurrency. Do not treat the historical report as a repeatable test suite or as proof of general deadlock freedom.

Shutdown stops polling and heartbeat scheduling, aborts the active task and in-flight API request, and waits up to five seconds for the task promise. If the promise does not settle, the worker retires and does not acknowledge. Deregistration marks its database row dead and can make a retry eligible; it does not prove process termination or external work termination. The worker process attempts to exit after deregistration, but external operations can outlive it. If deregistration fails, the row remains for operator recovery. Operators must verify or isolate the process and inspect external side effects before reconciling uncertain work. Lease expiry recovery can schedule another attempt while the old external operation may still be running.

Graceful deregistration uses the same retry-count rule and records a `timed_out` attempt for retryable or exhausted work. Duplicate completion and failure requests with the same token are accepted as successful only when that same attempt is already in the matching terminal state.

## Migration compatibility

Migration 004 adds lease token and expiry columns, worker credential hashes, plus indexes that enforce one active attempt per job and worker. Migration 005 adds the `cancelled` execution status. Migration 006 adds the `revoking` worker state and attempt revocation acknowledgement timestamp. Before starting its scheduler, recovery monitor, or HTTP listener, the API checks that the complete migration sequence from 001 through `007c_email_delivery_and_rate_limits.sql`, required enum labels, lifecycle columns, and critical indexes exist. It does not run migrations automatically. The migration runner requires PostgreSQL 12 or newer because enum values are added inside migration transactions. Follow [MIGRATION_PREFLIGHT.md](./MIGRATION_PREFLIGHT.md) before deployment. The runner commits each migration and its ledger insert together, but an earlier migration remains committed if a later migration fails. Rolling back the application to a pre-lease worker/API version is not safe; database rollback is not provided for these enum and credential/lease changes.
